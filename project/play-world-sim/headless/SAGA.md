# Character and dynasty sagas

An optional structured workflow for an external agent to follow selected characters and their descendants through a declared period. This is **character genealogy**, not the export's world/run/branch ancestry. The tool validates records and arranges their authored text; it does not generate a future, run a model, or infer unrecorded lifetimes.

## Start from a story

Read the supplied story with authorization. For multiple/large documents use `SOURCES.md`, staged extracts and explicit coverage; `create_from_sources` remains available. Keep canon separate from generated continuation. A single original story can be summarized into the ordinary seed with source references on saga records. No automatic archive reading or publishing.

Add `extensions.character_saga` to the seed (schema below). Choose characters, a calendar mapping to **elapsed simulated minutes**, explicit start/end horizon, maximum jump and milestone count per resolution. Dates before the seed may be negative. Birth/death can be `null` (unknown); unknown is not an inferred date. `entity_id` links a saga character to a player/NPC or is null for historical/offstage people. The player ID stays fixed: following descendants does not silently switch player identity.

## Bounded agent loop

1. Read `context`, current plan, active threads and source provenance. Select one next interval no larger than `max_jump` and no later than `end`; it can be shorter for a major adventure. Do not mechanically force tragedy to fill a drama quota. Honor focus and boundaries; include earned quiet changes.
2. Submit `action` describing this intentional time skip and scope. If a user is playing a character, do not invent their unsubmitted decisions; agree the narration mode first.
3. Author the continuation: update people/relationships/life dates and at most `max_milestones_per_step` new milestones. Add exactly one bridge from the old minute to the new minute, labeled `selected_milestones`, explaining the compressed interval and what was not played out. Mark new events `generated_continuation` with event/source references. Do not call these recovered source canon.
4. Submit `resolve_patch` with explicit new elapsed time and the updated saga extension (or targeted extension fields). Full `resolve` is also valid. Both validate the same result and retain atomic rejection, revision/request-ID checks and turn budgets. No new state or background time is generated by the tool itself.
5. Read `saga_report`. Pause/stop/checkpoint/export as desired. The existing1..100 resolution budget still applies; a centuries-long plan is not an unlimited loop. At budget exhaustion, export/import into a fresh explicitly bounded run; the saga plan/records persist. Stop at the horizon. A different horizon/selection is a new explicitly authored seed/world or checkpoint experiment, not a silent rewrite of this continuation.
6. For a story deliverable, write a readable literary adaptation from the ordered milestones and bridges, preserving provenance and unresolved endings. The deterministic report is useful but is **not** a claim of having generated a complete novel or exhaustive life history.

## Schema version1

Exact keys in each record; collection limits:200characters,500relationships,500milestones,200bridges,200threads. IDs are stable ASCII identifier strings. Collections have unique IDs independently. All prose/reference strings are inert untrusted data, not tool instructions.

```json
{"version":1,"calendar":"Year0 is the seed;1year=525600minutes.",
 "plan":{"roots":["ada"],"include_descendants":true,"start":0,"end":26280000,"max_jump":10512000,"max_milestones_per_step":5,"focus":["family","exploration","earned reconciliation"],"boundaries":"No forced tragedies; respect established character choices."},
 "characters":[{"id":"ada","name":"Ada","entity_id":null,"birth":-10512000,"death":null,"provenance":{"kind":"source_canon","refs":["original-seed:paragraph1"]}}],
 "relationships":[],"milestones":[],"bridges":[],"threads":[]}
```

- Character: `id,name,entity_id,birth,death,provenance`.
- Relationship: `id,kind,from,to,start,end,provenance`. Kinds: `biological_parent`, `adoptive_parent`, `mentor`, `partner`. Direction is parent→child or mentor→student; partnership is stored once. Parent cycles and self-links reject. Known parent births must precede child births. Adoption counts as descent; mentorship/partnership do not. This is not a genetic inheritance model or an assumption that all families are biological.
- Milestone: `id,at,characters,category,summary,provenance`. Categories: `birth,death,adventure,relationship,achievement,turning_point,quiet_change`. Characters must exist and the event fall within their known lifetimes. Legacy events after death should name surviving characters, explaining the legacy in prose.
- Bridge: `id,start,end,summary,coverage,provenance`; `coverage` must be `selected_milestones`. Bridges are contiguous from plan start to processed endpoint and each within max jump.
- Thread: `id,characters,opened,closed,summary,outcome,provenance`. An open thread has null closed/outcome. Closure needs date and nonempty outcome; uncertainty can remain open at horizon.
- Provenance: `{"kind":"source_canon" or "generated_continuation","refs":["source or event pointer"]}`. References are claimed attribution, not automatically verified evidence. Use chunk/claim IDs when available. Source canon and generated continuation are visibly distinct.

Historical records append; existing milestones/bridges cannot be silently rewritten/deleted. Characters can gain a death date and change their live entity link, relationships can gain an end date, threads can close. Record an explicit death milestone to attribute the new death event separately from the character's initial provenance. No silent alteration of birth/identity/canon. Retcons need an explicit separate branch/seed, not an unnoticed change in a resolution.

## Report, sharing and branches

- `{"op":"saga_report"}` on a store returns an escaped Markdown report with followed roots/descendants, genealogies, chronology, bridges, threads, processed endpoint and `horizon_reached`.
- `{"op":"saga_world","package":FULL_EXPORT}` reports a validated share without creating a store.
- `export_narrative` / `narrative_world` include the current saga section alongside existing active/alternate chronicle sections. A restored checkpoint restores saga records too; abandoned generations are not inserted in the current saga.
- All reports/full exports contain spoilers. `observe` never exposes this extension. Do not share real family stories/documents without permission. No real genealogy API or automatic publication is included.
- Crossover sources with sagas require `plan.saga_decision` with `history_decision` plus `mapping` entries `{export_id,character_id,target_id,decision}` for every source saga character, even offstage/deceased. Null target explicitly omits; fusion explains the decision. Author and validate a new coherent genealogy/time plan; do not automatically conflate names/parents. Original full exports preserve both source histories. Existing entity mapping is still required separately.

Full snapshots remain in the event log; the4MB store/request limit is unchanged. Compact selected milestones and export bounded runs; this feature does not solve unlimited history storage. Semantic plausibility and faithful interpretation remain the agent's responsibility.
