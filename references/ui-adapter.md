# Offline interaction demo
Open `assets/index.html` in a modern browser. No server, package install, or network call is required. This is an original floodgate scene and one predeclared sample check, not a complete campaign runner. Selecting an action creates a submission; the GM must determine whether it needs a check rather than applying the sample check to every action.

The explicit host integration contract is `window.freeformRpgSubmitNewTurn(jsonString)`. An embedding application must provide and test that callback before the send button is enabled. No undocumented ChatGPT API is assumed. Without the adapter, copy the exact structured payload into chat. The callback can fail after submission: inspect chat before retrying, and the canonical GM ledger must resolve a check ID only once.

The roller uses WebCrypto rejection sampling to avoid modulo bias. Local browser receipts prevent ordinary rerolls/reload resets for the same campaign/check pair. A client receipt is not a cryptographically verified campaign event: users can edit it, clear storage, switch devices, or restore an earlier export. Import/export only handles this sample's exact immutable check. A real host must restore canonical pending checks and reconcile receipts, never silently regenerate IDs to permit rerolls. The GM validates raw rolls against its stored rules; submitted totals and outcome labels are informational only.

The UI never renders imported text as HTML. File size is limited, core check fields are validated, and exported receipts contain no hidden GM secrets. It does not store the full campaign. Keep authoritative campaign files in an approved durable destination; receipt storage alone cannot ensure cross-chat continuity.

Tests: `node tests/test-ui.js` passes core assertions covering outcome precedence, partial success, malformed rolls/receipts, choice validation, and random rejection sampling. `node tests/browser-test.js` requires Playwright and Chromium. Browser tests were attempted but blocked by this execution environment's socket restrictions; visual layout and live host callback are unverified here. User previously reported that their original Instant interaction worked; that is not evidence this standalone implementation's host integration has been tested.

## Python engine contract
`assets/index.html` exports roll submissions with `campaign_id`, `scene_id`, `check_id`, and integer `raw_d20`. `scripts/engine.py:resolve` validates these against the canonical pending check and recomputes results. No `raw` alias is emitted. Informational fields are `modifier`, `total`, `dc`, and `outcome` (`success`, `partial`, or `failure`). The UI check matches the engine's `id`, named `modifiers` object, `partial_margin`, `natural_override`, and separate success/partial/failure stakes. The UI also carries campaign_id for routing.

Run `python tests/test_ui_engine.py` to exercise actual JavaScript-produced submissions through the Python engine for all twenty die results and verify duplicate resolution rejection. This test passes. Raw `extra_text` on action submissions should be carried to the declared check's action or the corresponding roll submission by the host if it contains dialogue the GM must preserve. Do not assign the sample check to every action.

Import validates the full immutable check and receipt. Conflicting imported die values are rejected without overwriting the existing receipt; an empty imported receipt cannot erase a stored result. This sample does not migrate older `raw`-named receipts: reconcile with the canonical GM ledger instead of rerolling.
